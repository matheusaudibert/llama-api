The API uses the Epic Games **device code flow**. The player never types a password into your bot: they open an official Epic page and approve the access.

## Session states

`POST /auth/device` creates a session and returns the `session_id`. From then on, the API waits for the approval in the background and the session goes through these states:

| Status | Meaning | What the bot should do |
|---|---|---|
| `pending` | Waiting for the player to authorize | Keep polling `GET /auth/{session_id}` |
| `completed` | Logged in | Call `/summary` and `/locker` |
| `expired` | The link expired without authorization (~10 min) | Ask the player to try again |
| `error` | Unexpected failure at Epic | Show the `error` field and ask for a new attempt |

## Polling

Poll `GET /auth/{session_id}` every 3 seconds. The API already checks Epic every 5 seconds, so a shorter interval does not speed anything up.

Stop polling when the status leaves `pending` or when the `expires_in` time returned at the start has passed.

```ts
async function waitForLogin(sessionId: string, expiresIn: number) {
  const deadline = Date.now() + expiresIn * 1000;
  while (Date.now() < deadline) {
    const { status, display_name } = await api<LoginStatus>(`/auth/${sessionId}`);
    if (status !== "pending") return { status, display_name };
    await new Promise((r) => setTimeout(r, 3000));
  }
  return { status: "expired" as const };
}
```

## Session lifetime

After the login, the session stays valid while both conditions hold:

- There was a call with the `session_id` in the last **30 minutes**.
- The Epic token has not expired. It lasts about **2 hours**.

During that time you can call `/summary` and `/locker` as many times as you want without a new login. After that, calls return `404` (session removed) or `410` (token expired).

<Tip>
  Call `DELETE /auth/{session_id}` as soon as you are done with the data. It revokes the token at Epic right away instead of waiting for it to expire.
</Tip>

## Security

- The Epic tokens give full access to the account. They **never leave the API**: responses only carry the `session_id` and the data that was read.
- The `session_id` is random (192 bits). Treat it as a secret: do not show it in public channels.
- Sessions live **in memory**. If the API restarts, every session is gone and players have to log in again. That is why you should run only **one instance and one worker**.
