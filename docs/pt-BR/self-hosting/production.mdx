O repositório já tem um `Dockerfile` pronto. Qualquer lugar que construa ou rode uma imagem Docker serve: uma VPS sua, uma plataforma como Railway ou Fly.io, ou um painel self-hosted como Coolify, Dokploy ou CapRover.

<Warning>
  Plataformas serverless, como Vercel e Netlify, não funcionam. A API guarda as sessões de login em memória e espera a autorização da Epic em background, então precisa de um processo que fique rodando.
</Warning>

## Pré-requisitos

- Um servidor ou plataforma que rode containers Docker
- Este repositório no seu GitHub (para plataformas que fazem o build a partir do repositório)
- Opcional: um domínio ou subdomínio, por exemplo `api.seudominio.com`, para servir a API com HTTPS

<Steps>
  <Step title="Gere a API key">
    ```bash
    python -c "import secrets; print(secrets.token_urlsafe(32))"
    ```

    Guarde o valor. Use a mesma chave no `.env` do seu bot.
  </Step>
  <Step title="Construa e rode a imagem">
    Em uma plataforma que faz o build pelo GitHub, aponte para o repositório, branch `main`, e escolha **Dockerfile** como método de build (`/Dockerfile`, contexto `/`).

    Em um servidor com Docker, rode:

    ```bash
    git clone https://github.com/seu-usuario/llama-api.git
    cd llama-api
    docker build -t llama-api .
    docker run -d --name llama-api \
      -p 127.0.0.1:8000:8000 \
      -e API_KEY="cole-a-chave-aqui" \
      --restart unless-stopped \
      llama-api
    ```

    O container escuta na porta `8000`.
  </Step>
  <Step title="Defina as variáveis de ambiente">
    | Variável | Obrigatória | Padrão | Descrição |
    |---|---|---|---|
    | `API_KEY` | Sim | | Chave que o bot envia no header `X-API-Key` |
    | `CATALOG_REFRESH_SECONDS` | Não | `21600` | Intervalo de recarga do catálogo do fortnite-api.com |
    | `LOG_LEVEL` | Não | `INFO` | `DEBUG`, `INFO`, `WARNING` ou `ERROR`. `DEBUG` também registra as chamadas a `/health` |
    | `LOG_FORMAT` | Não | `text` | `text` para linhas `chave=valor`, `json` para um objeto JSON por linha |

    <Warning>
      Sem `API_KEY` a API não inicia.
    </Warning>
  </Step>
  <Step title="Configure HTTPS">
    Coloque a API atrás de um proxy reverso com TLS. A maioria das plataformas gerenciadas já faz isso ao configurar um domínio. Em uma VPS, use Caddy, Nginx ou Traefik. Exemplo com Caddy, que emite o certificado automaticamente:

    ```text Caddyfile
    api.seudominio.com {
        reverse_proxy 127.0.0.1:8000
    }
    ```

    O uvicorn já roda com `--proxy-headers`, então os headers `X-Forwarded-*` do proxy são respeitados.

    <Tip>
      Se o bot roda no mesmo servidor ou na mesma rede Docker, ele pode chamar a API direto por `http://llama-api:8000` sem expô-la na internet.
    </Tip>
  </Step>
  <Step title="Configure o healthcheck">
    Se a plataforma pedir um healthcheck, use:

    - **Path**: `/health`
    - **Port**: `8000`

    O endpoint `/health` não exige API key. O `Dockerfile` também declara um `HEALTHCHECK` com `curl`, que o Docker e a maioria das plataformas reconhecem.
  </Step>
  <Step title="Teste">
    No primeiro start, espere nos logs:

    ```text
    Catalog loaded: 16599 cosmetics, 1018 banners
    Application startup complete.
    ```

    ```bash
    curl https://api.seudominio.com/health
    ```

    ```json Resposta
    { "status": "ok", "cosmetics_loaded": 16599, "active_sessions": 0 }
    ```
  </Step>
</Steps>

## Atualizações

As sessões ficam em memória, então **reiniciar o container desconecta quem estiver logado naquele momento**. Isso vale para deploys automáticos a cada push. Prefira atualizar quando o bot estiver com pouco uso.

Em um servidor com Docker, para atualizar:

```bash
git pull
docker build -t llama-api .
docker rm -f llama-api
# rode o mesmo docker run do passo 2
```

## Logs

A API escreve os logs no stdout, então eles aparecem no `docker logs` e no visualizador de logs da sua plataforma. Uma linha por requisição, mais os eventos de login e de sessão:

```text
2026-10-18 08:38:56 INFO    api.sessions  [55da3875054d] Login started session=5dbf3fb5 expires_in=600 active=1
2026-10-18 08:38:56 INFO    api           [55da3875054d] Request method=POST route=/auth/device status=200 ms=853
2026-10-18 08:39:40 INFO    api.sessions  [55da3875054d] Login completed session=5dbf3fb5 wait_s=44
2026-10-18 08:39:41 WARNING api.epic      [a1b2c3d4e5f6] Epic request failed what="athena profile" status=401 error_code=errors.com.epicgames.common.oauth.invalid_token
2026-10-18 08:40:02 INFO    api.sessions  [bot-123] Session removed session=5dbf3fb5 reason=logout status=completed token_revoked=True active=0
```

- O valor entre colchetes é o id da requisição. Envie o header `X-Request-ID` para usar o seu (por exemplo, o id da interação do bot); a API devolve ele no header `X-Request-ID` da resposta.
- `session` é um hash curto do `session_id`, suficiente para seguir um login entre as linhas. Tokens, session ids, emails e nicks nunca vão para o log.
- As rotas aparecem como modelo (`/auth/{session_id}`), nunca com o id real.
- `Epic request failed` traz o `error_code` da Epic, que costuma explicar a falha.
- `Session removed` diz o motivo: `logout`, `idle`, `token_expired` ou `shutdown`, e se a Epic invalidou o token.

## Não escale horizontalmente

Mantenha **uma réplica** e **um worker**. Com duas instâncias, um login criado numa não existe na outra e o bot recebe `404` aleatoriamente. O `CMD` do Dockerfile já roda o uvicorn com um único worker. Em plataformas com autoscaling, fixe o número de instâncias em 1.

## Recursos

A API usa pouca memória: cerca de 120 MB com o catálogo carregado. Uma instância com 512 MB de RAM é suficiente, inclusive dividindo o servidor com o seu bot.
